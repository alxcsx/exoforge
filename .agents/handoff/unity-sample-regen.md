# Refreshing the Unity sample's generated client (for whoever opens the Unity project)

Status: NOT done on purpose. The server-side database work (lldb / database / resource_store split, logical column
types, B1 boot isolation) changes no player-facing contract, so the sample keeps working as committed.
The new `lldb` actions (exec, provision_namespace, drop_namespace, transaction, introspect, dialect, table_columns) are
`scope(:server)` and do not reach the Unity client.

## Why a refresh is still worth doing once
`sdk/unity/sample_unity/Assets/Exoforge/Generated/ExoforgeServices.g.cs` was generated by an older generator.
Regenerating it from a live cluster (I tried, then restored the committed file) produced 10 service clients instead of
the committed 17:

    dropped: Dashboard, DashboardView, Database, ExtensionManager, FileBucket, Metering, Teste, Ws
    added:   Transport

Most of the dropped ones are staff/server services that the current generator moves out of the player-facing facade
(`ExoStudioServices`, Editor only). `Teste` looks like a leftover test service. I could not tell from here whether any
sample code uses a dropped client, so check before committing a regenerated file.

## Steps
1. Start a backend with an admin account, on a throwaway database (needs Docker/Podman or any Postgres):
       just db-up
       EXOFORGE_ADMIN_EMAIL=admin@local EXOFORGE_ADMIN_PASSWORD=<pw> EXOFORGE_SCHEMA_CHANGE_MODE=reset just dev
   (Do NOT use `just test-e2e`'s cleanup as a model: it runs `pkill -f beam.smp`, which kills every Erlang VM on the machine.)
2. Log in and put the token in `sdk/unity/sample_unity/Exoforge/exoforge.json` (environments.local.token), only for the run:
       curl -s -X POST http://127.0.0.1:4001/api/auth/login -H 'content-type: application/json' \
         -d '{"email":"admin@local","password":"<pw>"}'        # data.token
   Without a token `exo sync` silently falls back to local contracts and writes a much smaller file.
3. `just gen-client`  (runs `exo sync --dir sdk/unity/sample_unity/Exoforge`).
   It also copies `ExoCronAttribute.cs` into `Assets/Exoforge/Generated/Attributes/` (untracked): decide whether to keep it.
4. Restore `exoforge.json` to its committed content (token empty). Never commit the token.
5. In the Editor: let Unity compile, run the sample's tests / `just sample-check`, and look for compile errors that name a
   dropped client (`ExoServices.FileBucket`, `ExoServices.Database`, ...). Fix call sites or switch to `ExoStudioServices`
   inside `#if UNITY_EDITOR`.
6. Bump the SDK version if you change anything under `sdk/unity/Exoforge.SDK` (AGENTS.md rule 5).

## Other things that changed on the server that touch the sample
- Extensions now boot in isolation (B1): a broken extension is listed as failed/blocked in Studio instead of stopping the
  cluster. `extension_manager.list_extensions` carries `status` and `failure` per extension.
- Manifest columns carry a logical `storage` type (`int32`, `decimal`, `timestamp`, ...), `primary_key`, `unique`, `indexed`
  and a `schema_hash`. Nothing consumes them on the server yet (typed tables come with the resource_store work).
- `Exo.Database.QuerySql/ExecuteSql` (interpolated, parameterised SQL) and `Exo.Database.Transaction/ExecuteBatch`
  exist in the C# SDK; `[DbRead<T>]` / `[ExoForeignKey<T>]` declare cross-extension reads (generator side only so far).
