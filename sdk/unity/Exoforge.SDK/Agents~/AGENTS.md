# Exoforge Agent Operating Guide

This guide provides AI agents and developer tooling with essential architectural context and operational commands for working with the Exoforge backend within Unity projects.

## 1. Embedded CLI Execution

All backend operations are handled through the Exoforge CLI (`exo`). The root `./exo` wrapper is placed automatically by Unity (it is a dev tool, gitignored; `exo cli install` does the same by hand). AI tooling (`AGENTS.md` and skills) is **opt-in** and never installed automatically when importing `com.exoforge.sdk`.

- **Opt-In Installation**:
  - CLI: `dotnet Packages/com.exoforge.sdk/Editor/Cli~/exo.dll agents install --all` (or `--claude`, `--gemini`, `--agents`; running `exo agents install` with no flags prints help and installs nothing).
  - Unity Editor: **Exoforge ▸ Agents ▸ Install Agent Skills & CLI...** (or headless via `-batchmode -quit -nographics -executeMethod Exoforge.Unity.Editor.ExoforgeAgentTools.InstallAgentSkillsAndCliHeadless`).
  - Installations are idempotent and add a marked `.gitignore` block (`# >>> EXOFORGE-AGENT-TOOLING:START` / `# <<< EXOFORGE-AGENT-TOOLING:END`) covering the generated files.
- **Project Root Wrapper**: Once Unity has opened the project, execute `./exo <command>` directly from the Unity project root.
- **Embedded Package Fallback**: Before or without root wrappers, invoke the bundled CLI directly from `Editor/Cli~/`:
  - `Packages/com.exoforge.sdk/Editor/Cli~/exo <command>` (or `exo.cmd` on Windows)
  - `dotnet Packages/com.exoforge.sdk/Editor/Cli~/exo.dll <command>`
  - Or from the UPM cache: `dotnet Library/PackageCache/com.exoforge.sdk@*/Editor/Cli~/exo.dll <command>`
- **Structured JSON Output**: Always append `--json` to commands when programmatic parsing is required. JSON responses are written directly to stdout.

Example invocations:
```bash
./exo status --json
./exo contracts --json
./exo extension build my_extension --json
```

## 2. Project Topology

Unity projects integrate Exoforge using a strict boundary between client code and server extensions:

```
<UnityProjectRoot>/
├── Assets/
│   ├── Exoforge/
│   │   └── Generated/
│   │       └── ExoforgeServices.g.cs   # Strongly-typed client stubs generated by 'exo sync'
│   └── Resources/
│       └── exoforge.json               # Read-only runtime connection profile for game builds
├── Exoforge/
│   ├── exoforge.json                   # Workspace environments, cluster URLs, and auth tokens
│   └── extensions/
│       └── <extension_name>/           # Server-side C# extension projects (.NET 9+)
```

### Key Topology Rules:
1. **Server Extensions Live Outside `Assets/`**: Extension source code is located in `Exoforge/extensions/<name>/`. This keeps native C# backend projects completely isolated from Unity's AssetDatabase and Mono/IL2CPP compilers, allowing extensions to use modern .NET features and libraries.
2. **Client Stubs Inside `Assets/`**: Unity gameplay scripts only reference the generated client bindings in `Assets/Exoforge/Generated/ExoforgeServices.g.cs`. Never reference extension backend assemblies directly from Unity gameplay scripts. Gameplay scripts access services via `ExoServices.<Service>`; studio and admin services are separated into `ExoStudioServices.<Service>` guarded by `#if UNITY_EDITOR`.
3. **One Model, One Owner (extension dependencies)**: A model lives in the extension that owns it. Another extension that needs it depends on that extension; it never declares its own copy of the record. Use the generated stubs in `obj/exoforge/PluginServices.g.cs` (namespace `Exoforge.Plugins.Generated`, never committed): call `ExoServices.<Service>.<Action>Async(...)` and use the generated types (`Item`, `<Service><Action>Request`). The call, or naming a generated type while the file has `using Exoforge.Plugins.Generated;`, is the dependency; nothing else needs declaring, and a service you stop using drops out of the stubs. `CallAction<T>("service", "action", ...)` by name is a low-level fallback (no types, no compile-time checks): use it only when no contract can be generated. Building an extension builds the extensions it depends on first; if one fails, the build stops and names it, and a circular or excluded dependency is an error, so fix the named extension rather than working around it.
4. **Runtime Configuration**: The runtime connection settings reside in `Assets/Resources/exoforge.json`. These are generated and updated automatically by `exo sync` or via the Unity Editor menu.

## 3. Installed Agent Skills

When opted in via `exo agents install` or the Unity Editor menu, specialized agent skill instructions are installed into the selected skills directories (`.agents/skills/`, `.claude/skills/`, and/or `.gemini/skills/`) and ignored by git via the marked `.gitignore` block:

- **`exoforge-extensions`**: Full lifecycle of server-side C# extensions: scaffolding (`new`), compiling (`build`), deploying to the cluster (`push`), inspecting runtime outputs (`logs`), and updating client bindings (`sync`).
- **`exoforge-resources`**: Defining `[ExoResource]` entities, inspecting database tables, running migrations, and executing CRUD operations on cluster storage.
- **`exoforge-connection`**: Managing environments, configuring endpoints, discovering service contracts, running ad-hoc RPC actions (`exo call`), and troubleshooting connection issues.

## 4. Essential CLI Commands

| Command | Purpose |
| :--- | :--- |
| `exo agents install --claude\|--gemini\|--agents\|--all` | Opt in to installing selected AI skills, `AGENTS.md`, and the marked `.gitignore` block (no flags prints help). Also ensures the `./exo` wrapper exists. |
| `exo agents status --json` | Inspect installed agent tooling, skills, and CLI wrappers. |
| `exo status --json` | Inspect cluster connectivity, node status, and response latency. |
| `exo contracts --json` | List all registered service contracts, actions, and event schemas. |
| `exo sync` | Download cluster contracts and regenerate `Assets/Exoforge/Generated/ExoforgeServices.g.cs`. |
| `exo unity records --all` | Write `IsExternalInit.cs` per asmdef under `Assets/` that declares a `record` or `init` accessor (useful on fresh clones / CI). |
| `exo extension new <name> --template <type>` | Scaffold a new server-side extension (`persistent`, `basic`, `config`, `events`). |
| `exo extension build <name>` | Compile an extension assembly targeting the deploy runtime. |
| `exo extension push <name>` | Build, upload, and hot-load the extension into the active cluster. |
| `exo extension logs <name>` | Tail live standard output and standard error logs from an extension process. |
| `exo resource tables --json` | List database tables managed by cluster resources. |
| `exo resource list <table> --limit 20` | Query records from a resource table. |
| `exo resource create <table> --data '<json>'` | Insert a new record into a resource table. |
| `exo resource migrate` | Reconcile resource schemas with the cluster database. |
| `exo call <service> <action> --data '<json>' --json` | Invoke an action directly over RPC for validation and diagnostics. |
